# Verso 性能诊断报告

日期：2026-08-10
范围：主页、作品集页、图片数据接口、媒体资产链路、Vercel 公网环境
目标规模：当前约 2,203 个媒体条目，并为约 10,000 个媒体条目预留可扩展能力

## 1. 结论摘要

当前最严重的问题不是页面样式，而是媒体链路和数据加载方式：

1. 公网 Vercel Blob 存储当前返回 `403 Forbidden`，2,203 个媒体条目的图片都无法正常展示。公网测得的 LCP 很快，是因为图片根本没有成功下载，不能作为真实性能结论。
2. 作品页首次打开会连续请求全部分页，并把产品分类的 1,723 条完整记录全部下载到浏览器；现有“懒加载”只限制首屏渲染数量，没有限制数据获取量。
3. 每收到一页数据就用 `innerHTML` 整体重建首屏 60 张卡片，导致重复创建图片节点、重复请求和额外布局计算。
4. 列表接口返回了作品详情、EXIF、文件路径、标签等首屏不需要的完整字段；500 条记录的单页响应约 0.5 MB（解压后）。
5. 当前只有一档约 2,000 px 的 WebP 预览图，没有真正的缩略图层，也没有宽高元数据，因此无法在保持原始比例的同时稳定占位。

本轮将先完成不破坏数据的 P0/P1 优化：紧凑列表接口、服务端筛选和搜索、按需分页、取消重复重绘、骨架屏和图片稳定占位、响应缓存、详情按需获取。媒体存储恢复或迁移属于外部资源变更，必须在确认费用和目标存储后单独执行，本轮不会擅自迁移或删除原图。

## 2. 当前技术栈与架构

- Next.js 15 App Router、React 19、TypeScript。
- 作品页为 Next.js 页面中承载的遗留 HTML/CSS/JavaScript 界面。
- 作品索引位于 `public/generated/photo-library.json`，当前 2,203 条、34 个项目。
- 分类数量：摄影 480，产品摄影 1,723。
- 媒体索引约 2.22 MB；记录中的文件大小合计约 280.6 MB。
- 列表和详情当前共用同一个预览文件 URL，无 Thumbnail / Preview / Original 三层资源。
- 公网资源指向 Vercel Blob；当前 Blob 账户/存储因额度状态返回 403。
- 首页包含按交互才需要的 3D/动效组件，但当前被提前打入首页客户端资源。

## 5. 数据访问链路诊断

当前作品页链路：

`浏览器 -> /api/database?page=0..3&limit=500 -> 每页重建/排序全部数据 -> 返回完整对象 -> 浏览器持有 1,723 条 -> 每页到达后整体重建 60 个卡片 -> 直接请求 2,000px 预览`

建议链路：

`浏览器 -> /api/database?view=gallery&category=...&limit=24&cursor=... -> 服务端缓存索引并筛选 -> 返回紧凑卡片字段 -> 追加 DOM -> IntersectionObserver 请求下一游标 -> 点击卡片后按 id 获取完整详情 -> 列表加载 thumbnail，详情加载 preview，下载使用 original`

## 6. 分阶段修复顺序

### 第一阶段（P0）

- 新增兼容的紧凑 Gallery API，不破坏旧 API。
- 服务端缓存规范化索引，避免每页重复全量排序。
- 首屏只加载 24–30 条，取消首次全量四页请求。
- 改为追加 DOM，杜绝反复整体重建和重复图片发现。
- 详情字段改为点击后按需获取。
- 每一步后运行类型检查和生产构建。

### 第二阶段（P1）

- 服务端搜索、分类和标签筛选。
- 游标分页、请求取消、过期响应防抖。
- 骨架屏、加载状态、错误重试、稳定比例占位。
- API CDN 缓存和版本失效策略。
- 回填宽高元数据；原始文件只读，修改前备份索引。

### 第三阶段（P1/P2，依赖存储确认）

- 生成独立 Thumbnail / Preview / Original 三层资产。
- 先抽样 20 张校验尺寸、色彩、EXIF、URL，再批量生成和上传。
- 恢复 Vercel Blob 或迁移对象存储后，重新测量真实公网图片 LCP 和流量。
- 动态导入首页 3D 组件，减少字体和强制回流。

## 7. 数据安全承诺

- 不删除、不覆盖、不移动源照片。
- 不改变现有作品 ID、分类和已有访问路径。
- 对生成索引的任何批量更新先建立带时间戳备份。
- 缩略图和预览图只作为新增派生文件，不替代原图。
- 存储迁移、批量上传和永久 URL 调整必须单独确认后执行。
- 优化后抽样核对作品数量、分类数量、ID 唯一性、URL、EXIF 和详情页打开行为。

## 8. 验收口径

代码阶段验收以以下指标为准：

- 首屏数据请求由 4 次全量页改为 1 次紧凑页。
- 首屏浏览器不再持有全部 1,723/2,203 条记录。
- 初始 DOM 作品卡片控制在 24–30 个，后续按需追加。
- 不再因数据页到达而反复重建已显示卡片。
- 搜索、分类、详情、导航和作品打开行为保持可用。
- TypeScript 类型检查、生产构建通过。
- 图片存储恢复后再补充真实公网 After LCP、图片流量和 Core Web Vitals。

## 9. 已实施的优化

### 作品库

- 新增兼容的 `view=gallery` 游标接口，首批默认只返回 24 条紧凑记录。
- 新增 `view=detail&id=...` 详情接口，相机、镜头、描述、标签等只在打开作品后获取。
- 原来的数组接口保持不变，已有后台和遗留页面仍可继续使用。
- 搜索、主分类和子分类移到服务端执行，不再先把全部数据拉到浏览器再 `filter()`。
- 生成索引在服务启动时只规范化、去重和排序一次。
- 列表响应增加 `s-maxage=300, stale-while-revalidate=3600`。
- 作品页从四个 500 条全量请求改为 IntersectionObserver 游标分页。
- 首屏 24 张，滚动接近底部后才追加下一批；不再因每页到达而整体重建现有卡片。
- 增加骨架占位、加载进度、空结果、失败重试和请求取消。
- 第一张首屏图使用高优先级，其余图片按视口懒加载。
- 详情弹窗改为按需请求完整元数据。
- 修复语言切换器覆盖动态加载状态和详情文本的问题。

### 图片元数据与稳定布局

- 修改前备份了完整媒体索引和准备记录。
- 从只读 WebP 派生预览中回填 2,202 张图片的 `width`、`height`、`aspect_ratio`。
- 唯一未回填宽高的是 1 个 MP4 视频，媒体记录本身保留不变。
- 作品卡片按真实比例预留空间，图片下载前先显示轻量骨架。
- 原图、现有公网 URL、作品 ID、标题、分类、EXIF 和历史路径均未修改。

### 首页

- 联系关系图谱和灵感 3D 空间改为真正的交互后动态加载；首次打开首页不再下载 Three/R3F 等大块脚本。
- 首页 First Load JS 从约 354 KB 降至约 106 KB。
- 本地首页大图使用 Next.js 图片派生服务：分类封面 640 px、卡片 1,080 px、Hero 1,920 px；原文件和原访问路径保持不变。
- `archive-collage.png` 的 640 px 页面版本从约 3.2 MB 降至约 113 KB。
- 导航滚动不再持续读取 `hero.offsetHeight`；推荐轮播的 resize 更新增加动画帧节流。

## 14. 10,000 张扩展判断

当前方案已不再让浏览器成本随总媒体数线性增长：首屏始终是 24 条、1 个紧凑请求和约 24 个卡片，服务端搜索/分类也不要求下载全量数据。以当前静态索引方式可支持 10,000 条浏览与筛选，但到 10,000 张时建议执行以下第二阶段基础设施升级：

1. 将媒体索引迁入 PostgreSQL/Supabase，建立 `(category_slug, sort_order, id)`、标题和标签搜索索引。
2. 对列表使用稳定 ID/排序字段的数据库原生 Cursor Pagination，而不是内存筛选。
3. 在对象存储中建立 Thumbnail / Preview / Original 三层不可变路径，并在数据库记录宽高、格式、字节数和版本。
4. 深度浏览达到数百个节点后引入虚拟瀑布流或分段回收；当前按需追加适合普通浏览，但用户滚动到第 10,000 张时 DOM 仍会累计。
5. 为媒体索引和缩略图设置版本化长缓存；上传完成后只失效受影响的分类游标页。
6. 增加真实用户监控，持续记录 LCP、INP、CLS、失败图片率和每次会话图片流量。
